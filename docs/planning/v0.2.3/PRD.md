## 1. 目标与用户价值

面向中小企业品牌负责人、个人品牌和公关/营销人员，减少监测配置门槛，并把分散的舆情原文组织成可追溯的事件演化过程。用户应能以少量业务信息启动监测，并理解事件**何时出现、如何传播、观点怎样变化、回应后有何变化**，为后续 Multi-Agent Forum 的研判提供可核验的事实依据。

本版本的两项功能均属**规划需求**；涉及数据覆盖、实时性或 AI 输出的能力，以实际接入的数据源和验收结果为准，不将方案描述视为已上线能力。

## 1.1 beta 0.2.3 交付决策（2026-09-28）

**两层均须兑现**：六类模板不仅预填既有的四类分析视角，还必须使用户确认的关键词、排除词、数据源、监测周期、风险标签、预警规则与报告模板在实际采集、分析、通知及报告生成中生效；不允许仅保存配置或做 UI 演示就算完成。用户选择周期执行时必须有持久调度、幂等执行及明确的扣费/用量提示；用户选择启用预警时必须有可验证的送达记录。暂不默认给所有方案自动开启周期执行或通知，须经用户明确确认。

四种 `analysis_type` 保留为研判视角，六种 `template_id` 为可编辑的方案场景。默认映射：品牌日常口碑（`brand_daily`）→`brand`、新品上市（`product_launch`）→`event`、产品质量投诉（`quality_complaint`）→`brand`、竞品动态（`competitor_update`）→`competitor`、突发危机（`crisis`）→`event`、营销活动复盘（`campaign_review`）→`event`。`industry` 继续保留在手动创建入口；模板向导展示默认视角且允许修改，避免让用户重复选择两个“类型”。营销活动与新品也可以在修改后采用 `brand` 视角，产品质量投诉如变成单次危机可改选 `event`，不改变模板 ID；历史分析任务值及原入口保持兼容。事件时间线是否有节点取决于真实证据，不由 `analysis_type=event` 自动填充。

**版本验收口径**：七项配置必须分别能追踪其实际生效状态、执行结果与异常说明。任一需要的执行能力缺失时显示“不可用/未启用”，不得宣称 beta 0.2.3 两层交付完成。
## 2. 功能一：监测方案模板化（P0）

### 2.1 问题与范围

传统配置依赖用户理解关键词、布尔查询、排除词及数据源，首次使用成本高。参考识微商情、清博等产品的监测方案、预警规则、标签组和报告模板思路，本版本规划将场景经验沉淀为可预览、可修改的监测方案；不是承诺竞品的具体覆盖规模或实时效果。

首批提供六类场景模板：

| 模板 | 主要关注点 |
|---|---|
| 品牌日常口碑 | 品牌提及、评价及持续变化 |
| 新品上市 | 新品相关讨论、反馈与风险 |
| 产品质量投诉 | 质量问题、投诉与重复诉求 |
| 竞品动态 | 竞品提及及主要变化 |
| 突发危机 | 特定事件的负面扩散与风险变化 |
| 营销活动复盘 | 活动期间的讨论、反馈与传播结果 |

### 2.2 用户流程

1. 选择关注场景及对应模板，输入**品牌名、产品名、竞品名、行业、关注场景**；仅填写所选模板适用的信息，缺少非必填信息不阻塞创建。
2. 系统生成方案草稿并展示生成依据；用户可查看、编辑和确认，不应在确认前悄悄启用监测或发送预警。
3. 用户确认后保存方案，将其应用到已有监测任务能力；后续可查看和调整配置。

### 2.3 自动生成内容

| 配置项 | 预期行为 |
|---|---|
| 关键词 | 基于品牌、产品、竞品与场景给出建议；避免无依据扩展同名词 |
| 排除词 | 识别明显歧义或噪声，允许用户编辑，不能默认排除重要原文 |
| 数据源 | 仅推荐当前实际可用、获得授权的来源；显示可用状态及更新限制 |
| 监测周期 | 给出适合场景的时间范围/执行频率供确认，不承诺未验证的实时性 |
| 风险标签 | 预置场景相关风险类别，保留可编辑入口 |
| 预警规则 | 输出触发条件、频率和通知方式的草稿；遵守现有权限与套餐约束 |
| 报告模板 | 关联匹配场景的报告结构，明确哪些输出需要数据支撑 |

### 2.4 验收标准

- 六种模板均可选择并生成包含上述七类配置的方案草稿；品牌、产品、竞品等输入能在适用模板中正确对应，不串入其他租户的数据。
- 创建前可逐项预览并修改生成内容；确认后能保存和再次打开，重试创建不会意外产生多个生效任务或重复扣费。
- 某来源不可用或当前套餐不支持时有明确提示，不把不可用来源显示为已覆盖，不以模拟结果充当真实监测。
- 输入含歧义或缺少非必填字段时，给出可操作提示；生成失败时不创建半成品生效任务、不静默启用错误预警。
- 验证从选择模板到**提交可运行方案**的用时与成功率；是否达到“5 分钟内完成配置”需在真实用户试用中实测，非本 PRD 的既成事实。

## 3. 功能二：事件时间线与传播链路（P0，数据可得性前置）

### 3.1 问题与目标

当前用户需要看到的不只是若干原文摘要，还应能还原事件生命周期、传播节点与数据溯源。参考清博、数说故事对事件过程的呈现思路，为同一事件组织有证据的节点，使 Multi-Agent Forum 基于真实的时间与传播线索研判，而非仅对一批文本进行抽象总结。

### 3.2 事件视图

按事件发生的实际时间顺序展示；以下是**可识别时**应呈现的节点类型，不表示每个事件都必然经过全部阶段：

```text
首次出现 → 首次传播 → 关键账号扩散 → 观点分化
         → 负面爆发 → 品牌回应 → 回应后的舆情变化
```

每个节点展示可获得的时间、来源平台、原文/链接、账号或传播主体、对应证据及分类理由；首次出现与首次传播只表示**已采集数据中可核实的最早记录**，不得声称是全网绝对首发。节点不可识别时标注“暂无足够证据”，不补造阶段。以来源链接、相同内容/引用关系等可核验信号连接传播节点；仅时间相近不能推断转发或因果关系。观点分化与负面爆发等 AI 研判节点应标示证据及不确定性。

品牌回应须关联可验证的官方内容；“回应后的舆情变化”展示观察窗口及回应前后数据对照，不把相关性写成回应导致的因果结论。跨平台传播取决于来源的实际接入与可验证的引用关系，未覆盖平台需明确标示。

### 3.3 验收标准

- 用户可从事件查看按时间排序的节点；每个展示的节点可回到本租户可访问的原文或来源记录，并区分来源事实、模型推断与不可验证信息。
- 可在已有可靠引用/转发证据时查看传播关系；没有关系证据时不绘制臆测链路，节点缺失或来源不可用时显示数据缺口。
- 同一原文的重复采集不应产生多个“首次出现”节点；多租户用户无法读取彼此的事件、来源与报告。
- 存在真实官方回应时展示回应节点及回应前后的观测数据；不存在时不自动生成品牌回应。
- Forum 在引用时间线时只引用可追溯内容；降级或部分采集失败保留可用原文并显式提示，不得生成伪造引用或模拟传播路径。

## 4. 边界、依赖与待定项

- **不在本次规划中承诺**：全网绝对首发识别、所有平台实时采集、自动判定转发因果、自动发布品牌回应或基于不完整数据推断完整传播图谱。
- 复用现有监测任务、数据采集、报告和 Forum 能力的前提是当前实现与租户/权限/计费契约经开发评估确认；本 PRD 不宣称上述能力当前已具备或已在生产环境验证。
- 开发前需确认：各来源的时间戳/原文链接/作者及引用关系是否足够可靠；现有预警和报告配置如何映射；官方回应由谁录入及如何校验；六类模板各自哪些字段必填；数据缺口的用户提示方式。
- 上线前应分别验证真实来源采集、配置可编辑、租户隔离、计费幂等、降级标识与引用真实性；模拟或单元测试通过不代表外部数据源已经验证。
