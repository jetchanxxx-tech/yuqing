「热榜」聚合页方案 定稿 · 待开发

2026-09-15 产品经理 × 开发总监碰撞定稿，创始人批准。范围红线：本页面只做多平台热榜快照展示，上轮订阅/个性化/计费融合方案作废。

1. 定位

登录用户均可看的多平台实时热榜快照页。零存储、零计费、零 LLM。成功标准唯一：日打开率。

2. 页面（产品）

项决策
形态Tab 切换（不做聚合流 —— 各平台第 1 名不可比，保护排名语义）；Tab 由后端平台清单数据驱动
平台顺序微博 → B站 → 知乎 →（实测达标后）抖音、小红书；不达准入线不上线、不留灰 Tab
条目排名 + 标题（即外链，新窗口）+ 热度值；Top3 标色；不显示逐条时间（数据没有，不装），列表级「更新于 HH:MM」
三态ok 正常 / stale 旧数据 +「更新于 X 分钟前」/ error 空态 + 重试。宁可示弱不可装死
刷新切 Tab 拉取 + 手动刷新按钮；服务端共享 TTL 5 分钟；固定弱提示「实时快照，不保留历史」
命名/入口「热榜」/trends；导航第二位（仪表盘之后），不改默认落地页
钩子条目 hover「分析」图标 → 跳新建分析页预填关键词（≈带参数链接，扣额度走正常流程，本页不弹窗不感知额度）

3. 范围红线（不做）

不订阅、不落库、不碰计费、不做 LLM、不做推送/大屏/移动端、不开放任意 RSS 路由自由订阅。

4. 技术（开发）

RSSHub 自建 unit (127.0.0.1:1200, 仅 loopback)
  → Go server 内存缓存 map[平台]*Feed，后台单 ticker 每 5min 刷全部
     （每平台独立 10s 超时 + recover；失败保留 last-good 置 stale）
  → GET /api/v1/trends  纯内存返回（JWT 必需，错误也 200+error 态）
  → 前端 TanStack Query 60-120s 轮询 + Tab 渲染
  • 结构：internal/business/trends 新包，与 analysis 零耦合；Item{Rank,Title,URL}；内存 <1MB 不淘汰
  • 重启行为：缓存清零不补偿，启动即首轮刷新，5-15s 内首屏可用
  • 不引入 SSE/ETag/消息队列 —— 此规模均为过度设计

5. 路由准入（0.5 天 spike）

平台路由免Cookie置信度
微博/weibo/search/hot是高
B站/bilibili/hot-search是高
知乎/zhihu/hotlist是中高
抖音热点榜路由待核实否低（严格反爬+Puppeteer）
小红书大概率不存在或不稳—低

准入线：免 Cookie、≥20 条、<15s。不达标 Tab 显示「即将上线」或砍。若抖音/小红书全灭 → 生产不装 Chromium（省 300-400MB）。

6. 部署

  • yuqing-rsshub.service：低权用户、只绑 127.0.0.1:1200（绝不暴露公网）、MemoryHigh=700M/MemoryMax=900M、Restart=on-failure
  • 生产零构建：dev 机构建 tarball（dist+node_modules）推送；版本钉 git tag + 月度路由冒烟脚本
  • 四坑沿用：tarball 推送 / Ubuntu 24.04 chromium snap 陷阱（npx puppeteer browsers install chrome）/ 低权用户 / MemoryMax
  • 若需 Chromium：池钉死 1，与 analysis 管线浏览器共享全局信号量
