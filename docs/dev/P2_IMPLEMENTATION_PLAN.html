二、架构变更

2.1 迁移 0008 SQL

-- +goose Up
-- 报告中心 + 用户归属：新增 created_by 列支持报告多版本与用户隔离

-- 1. analyses 表新增 created_by（UUID，nullable → 非空回填见 CLI）
ALTER TABLE analyses ADD COLUMN created_by UUID REFERENCES users(id) ON DELETE SET NULL;

-- 2. reports 表新增 created_by（UUID，nullable）
ALTER TABLE reports ADD COLUMN created_by UUID REFERENCES users(id) ON DELETE SET NULL;

-- 3. reports 表新增 report_version（INTEGER，版本号用于多报告对照）
ALTER TABLE reports ADD COLUMN report_version INTEGER NOT NULL DEFAULT 1;

-- 4. 回填历史数据：analyses.created_by 从 members 表关联（tenant_id + 租户第一个成员）
WITH first_member AS (
  SELECT tenant_id, user_id,
         ROW_NUMBER() OVER (PARTITION BY tenant_id ORDER BY created_at) AS rn
  FROM members
)
UPDATE analyses a
SET created_by = fm.user_id
FROM first_member fm
WHERE a.tenant_id = fm.tenant_id AND fm.rn = 1
  AND a.created_by IS NULL;

-- 5. 回填历史数据：reports.created_by 从 analyses.created_by 继承
UPDATE reports r
SET created_by = a.created_by
FROM analyses a
WHERE r.analysis_id = a.id AND r.created_by IS NULL;

-- 6. 非空约束（回填后）
ALTER TABLE analyses ALTER COLUMN created_by SET NOT NULL;
ALTER TABLE reports ALTER COLUMN created_by SET NOT NULL;

-- +goose Down
ALTER TABLE reports DROP COLUMN IF EXISTS report_version;
ALTER TABLE reports DROP COLUMN IF EXISTS created_by;
ALTER TABLE analyses DROP COLUMN IF EXISTS created_by;
说明：
  • analyses.created_by 在创建时由 analysis.Service.Create 从 req.UserID 写入
  • reports.created_by 在管线调 CreateFromAnalysis 时写入
  • 历史回填由 CLI 单独执行，不阻塞迁移

2.2 Rerun 多报告策略

决策：同 analysis_id 多行报告，report_version 字段区分版本，created_at 排序

字段说明
idULID，每次 CreateFromAnalysis 新建
analysis_id关联分析 ID（不变）
report_version版本号（同一 analysis 的第 N 次报告）
formathtml / docx
statuscompleted / failed
created_at创建时间（排序用）
created_by创建人 UUID

报告列表排序：ORDER BY created_at DESC，最新版在前。用户可对照任意两个版本。

2.3 docx 生成位置

决策：Python report_engine 生成（python-docx 成熟稳定），Go 侧流式代理下载

  • Python report_engine/main.py 新增 /generate_docx 端点，输入同 /generate，输出 docx 二进制流
  • Go report.Service.DownloadURL 返回 /tenants/{id}/reports/{id}/download?format=docx
  • Go HTTP handler 流式转发 Python 返回的 docx 二进制（避免大文件内存峰值）
  • python-docx 生成 docx 文件写入 /tmp/reports/{report_id}.docx，Go handler 从该路径读取并设置 Content-Disposition: attachment
为什么不纯 Go 生成：HTML 模板已有完整渲染逻辑，python-docx 直接复用报告结构，Go 侧重写成本高且易引入不一致

2.4 历史回填策略

决策：仅 HTML（从 analyses.report_content 提取），docx 不回填（需重跑 LLM，成本过高）

-- 回填 CLI：读取所有 completed analyses，提取 report_content 生成 report 记录

3.1 P0 报告中心空白 — 管线调 CreateFromAnalysis

问题根因

platform/internal/business/analysis/pipeline.go:269 只调用 svc.SetReport()（写 analyses.report_content），从不调 report.Service.CreateFromAnalysis()，导致 reports 表零行。

修复方案

Step 1：修改 pipeline.go 的 runReport 方法，管线完成后调 report.Service.CreateFromAnalysis()

// runReport 末尾新增（pipeline.go ~269行）：
// 管线只写 analyses.report_content（维持现状）
// 新增：同步创建 reports 表记录
if res.Content != "" {
    // 创建 HTML 报告记录
    r, err := p.reportSvc.CreateFromAnalysis(ctx, msg.TenantID, msg.AnalysisID, "html")
    if err != nil {
        p.log.Warn("pipeline: create report record failed", slog.String("err", err.Error()))
        // 非致命：analyses 已写入，报告内容不丢
    } else {
        p.log.Info("pipeline: report record created",
            slog.String("report_id", r.ID), slog.String("analysis_id", msg.AnalysisID))
    }
}

Step 2：Go HTTP download handler 流式代理 docx（platform/internal/api/v1/reports.go）

GET /tenants/:tenant_id/reports/:report_id/download?format=html|docx
  → 读取 reports 表 FileKey
  → HTML: 直接返回 analyses.report_content
  → docx: HTTP GET {report_engine}/download/{file_key} → 流式转发响应头 + body
  → Content-Type: application/octet-stream
  → Content-Disposition: attachment; filename="report_{id}.{format}"

3.2 P0 数据源标签错标 — 域名正则分类

问题根因

engines/common/scraper.py:106-107：all_candidates[sources[0]] = found — 所有 Bocha 搜索结果被强制归类为用户勾选的第一数据源，即使来源是其他平台。

修复方案

Step 1：修复配额截断 bug（scraper.py ~116行）

# 错误：按 source 顺序处理，每个 source 取前 max_per_source
# 正确：先收集所有结果，再按全局优先级截断
candidates = all_candidates.get(source, [])[:max_per_source]  # BUG: 勾选越多结果越少

# 修复：合并所有 source 的候选，再按全局 max_per_source 截断
all_urls = []
for src, cands in all_candidates.items():
    for cand in cands:
        all_urls.append((cand.get("url"), src))
# 全局去重 + 截断
unique_urls = _dedupe_by_url(all_urls)[:max_per_source * len(sources)]

Step 2：按 URL 域名自动分类

import re

DOMAIN_SOURCE_MAP = {
    r"weibo\.com|sina\.com\.cn": "weibo",
    r"mp\.weixin\.qq\.com": "weixin",
    r"xiaohongshu\.com|xhslink\.com": "xiaohongshu",
    r"bilibili\.com|b23\.tv": "bilibili",
    r"douyin\.com|iesdouyin\.com": "douyin",
    r"kuaishou\.com|ksurl\.cn": "kuaishou",
    r"zhihu\.com": "zhihu",
    r"36kr\.com": "news",         # 36氪归新闻
    r"sina\.com\.cn/news": "news", # 新浪新闻归新闻
    r"news\.|newspaper\.": "news",
}

def classify_by_domain(url: str) -> str:
    """根据 URL 域名推断数据源类型"""
    for pattern, source in DOMAIN_SOURCE_MAP.items():
        if re.search(pattern, url, re.IGNORECASE):
            return source
    return "custom_web"  # 未知来源

# 应用：_bocha_search 返回的每个结果按域名分类
for item in bocha_results:
    item["source_type"] = classify_by_domain(item["url"])

Step 3：用户勾选来源作为「过滤」而非「分类」

# 用户勾选决定「允许哪些来源」，不决定「结果归哪类」
# Bocha 搜索返回所有结果 → 按域名分类 → 过滤用户勾选之外的数据源
final_results = [
    doc for doc in classified_results
    if doc["source_type"] in user_selected_sources
]

3.3 P1 面板数据不分用户 — Sources/Topics 真实计算

问题根因

platform/internal/business/dashboard/service.go:14-27：fixedSources 和 fixedTopics 是硬编码"雅阁后排"占位数据，从不计算真实文档来源。

修复方案

Step 1：documentStore 新增按 tenantID 聚合方法

// platform/internal/business/analysis/store.go 新增接口
type documentStore interface {
    // ... 现有方法 ...
    ListByTenant(ctx context.Context, tenantID string) ([]Document, error)
    AggregateSources(ctx context.Context, tenantID string) ([]SourceShare, error)
    AggregateTopics(ctx context.Context, tenantID string) ([]Topic, error)
}

Step 2：PG 实现（store_pg.go）

-- AggregateSources SQL
SELECT
    COALESCE(doc.source_type, 'custom_web') AS source,
    COUNT(*) AS doc_count
FROM raw_documents rd
JOIN analyses a ON rd.analysis_id = a.id
WHERE a.tenant_id = $1 AND a.state = 'completed'
GROUP BY rd.source_type
ORDER BY doc_count DESC;

-- AggregateTopics SQL
SELECT
    t.name,
    t.doc_count,
    t.trend
FROM topics t
JOIN analyses a ON t.analysis_id = a.id
WHERE a.tenant_id = $1 AND a.state = 'completed'
ORDER BY t.doc_count DESC;

Step 3：dashboard/service.go 替换硬编码

func (s *Service) Sources(ctx context.Context, tenantID string) (*SourceBreakdown, error) {
    if s.docStore == nil {
        return &SourceBreakdown{Sources: fixedSources}, nil // 降级
    }
    return s.docStore.AggregateSources(ctx, tenantID)
}

func (s *Service) Topics(ctx context.Context, tenantID string) ([]Topic, error) {
    if s.docStore == nil {
        return fixedTopics, nil // 降级
    }
    return s.docStore.AggregateTopics(ctx, tenantID)
}

七、关键技术决策汇总

决策点选项 A选项 B（选）决策理由
docx 生成位置Go 侧（新依赖）Python report_engine复用现有 HTML 模板结构，python-docx 成熟稳定
Rerun 多报告策略覆盖旧报告每次新建报告记录保留新旧对照能力，符合用户决策
下载端点预签名 URL流式传输无对象存储（本地 FS），流式代理避免内存峰值
历史回填重跑 LLM 生成 docx仅 HTML（已有）docx 回填需重跑 LLM，成本过高且可能超时
source 分类用户勾选决定URL 域名正则Bocha 无 source 参数，域名是最可靠分类依据
面板真实计算时机实时聚合documentStore 聚合查询raw_documents 已按 analysis_id 索引，tenant 级别聚合成本可控
