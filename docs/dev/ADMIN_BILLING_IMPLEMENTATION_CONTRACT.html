1. 业务规则与边界

规格：管理员与用户中心开发计划、2026-10-09 已确认业务规则，以及项目 AGENTS.md。本文覆盖原计划中 K4、D1 的旧公测假设；K1／K2 的实时身份、账号／租户状态和权限约束继续适用。

架构：沿用 Go／Gin／pgx／goose 与 PostgreSQL 15。固定身份政策、套餐解析、报告次数账本和供应商用量各有独立职责；分析准入把它们连接到同一 PG 事务。Python 共同 LLM 层通过内部接口获取本轮调用许可并交付可重投的用量事件。

  • 固定豁免绑定核对后的不可变 users.id。Email 只用于一次定位与核对，不在业务请求中决定豁免；不扩展到其他平台管理员、同团队成员或整个 tenant。
  • 固定管理员可在报告额度为零或消费配额已满时创建／重跑；实际余额保持真实值，不能赠送巨大余额、把整个团队升级成免费 Enterprise，或把后台管理权限等同于计费豁免。
  • 普通账号 Create／每次用户主动 Rerun 消费 1 次报告额度，失败／取消按当前轮实际消费精确回补；支付金额与发放次数沿用服务端套餐目录。
  • 豁免不绕过账号或租户非 active 状态、成员关系、API Key 撤销、接口权限、数据隔离及已有服务资源保护。固定身份仅影响次数／消费限制和用户费用。
  • 所有实际供应商调用记录真实 token、模型、供应商成本、调用身份和轮次。免计费不等于不记录；免计费用量不得消耗同团队普通成员的套餐配额。
  • 本轮通知和支付适配器使用沙箱：不得实发邮件／短信或实际付款。既有套餐次数收费的实现与验收不依赖真实支付或真实价格联调；真实供应商送达、付款和真实模型成本对账保留为单独未验证项。
实施方法：每个下列任务先提交行为 RED 用例，经指定 GitHub 托管工作流确认失败，再实现到 GREEN、独立复核和记录证据。已授权的顺序实施无需重新申请方案许可；涉及认证文件的改动须等待 K1 worker 完成并按已冻结接口衔接。

必须在测试中覆盖的五种交叉情形

  1. 普通成员、另一平台管理员和固定管理员共用 tenant，只有固定 UID 的本轮发起人免费。
  2. 普通付费完成轮次之后管理员免费重跑失败，不退旧的成功消费。
  3. 重跑并发、旧消息重投和 worker 重启，不重复扣费，也不让旧轮消息推进新轮状态。
  4. API Key 主体与真实创建者不同；未知历史创建者不能获得豁免或伪造 analyses.created_by。
  5. 供应商已产生用量后发生 JSON 解析失败、任务取消或事件回传失败，成本仍记录且重投不重复记账。

历史数据与切换

  • 旧已接纳分析按可信 analyses.created_by 生成可追踪历史轮次。仅有明确、一对一的当前消费证据才关联旧 consume；无扣费的旧公测轮次标记 legacy_unbilled，禁止追扣、补造收费或重置余额。
  • 旧流水无法明确证明轮次时保留原账本并列入待对账清单；新退款路径不擅自领取这类旧消费。历史财务事实不能被 K4 覆盖。
  • 切换时停止接纳新任务，协调 server／worker 同版和迁移；确认旧排队任务的 run 映射。旧缺 run_id 消息只可匹配仍为 legacy_unbilled 的当前历史轮次；分析已进入新轮后旧消息是 no-op 并记录审计。
  • 后续用户 Rerun 一律创建 normal 或 fixed-UID exempt 新轮。历史免费模式不构成任何账号未来使用的豁免。

4. 固定身份与 API Key

一次绑定 CLI

yuqing-cli bind-billing-exempt-admin --expected-user-id <verified-users.id>
yuqing-cli bind-billing-exempt-admin --expected-user-id <verified-users.id> --apply

无 apply 只做预检。apply 在 PG 事务内直接查询唯一 admin@pangu.com 账号，核对与 expected-user-id 相同、账号有效以及管理员身份来源真实，写固定政策与审计。该核对不是读取调用方 JWT email，也不等同于要求发送新的验证邮件。绑定到同一 UID 重放幂等；已绑定别的 UID 返回 409，不能覆盖。后续改邮箱不改变豁免 UID，新建同邮箱账号不能继承。

运行政策解析只用绑定 UID 和可信本轮 actor；lookup 失败应拒绝准入，不能自动免计费。政策表为空则所有新轮正常收费。普通业务接口不能接受 policy_key／exempt／charge_mode。固定账号即使持有管理角色以外的角色，也不把角色本身当成豁免条件；账号和租户状态仍按 K1／K2 阻断。

API Key 的身份分工

  • 认证主体：apikey:<key_id> 与 api_service／Key scopes 保持独立；保存 creator 不授予 Key 平台管理员权限，也不允许 Key 进入用户换密／换邮箱／注销。
  • 计费 actor：从已验证 Key 元数据读取 immutable creator_user_id；服务端再次检查该用户、成员关系、Key 与 tenant 当前状态。不能从请求 JSON、Key 名称、tenant plan 或 email 推断。
  • 资产创建者：Create 写入真实 creator_user_id，满足 analyses.created_by 外键；本轮保存 actor_api_key_id 供审计。普通 JWT Create 写登录用户 ID。
  • 历史未知 Key：只要旧权限和 tenant 状态允许，可保留既有只读能力；Create／Rerun／LLM 新消费及创建子 Key 返回 403 API_KEY_OWNER_UNVERIFIED，提示重新签发。不能假造用户记录或借整个 tenant 免计费。
  • 固定管理员本人签发的 Key：仅可信 creator 命中固定 UID 才继承该账号的账务豁免；同 tenant 其他用户签发的 Key 正常收费。Key 撤销或 creator 失效后不能开始新调用。

Create／Rerun 的唯一准入事务

  1. 服务端构造可信 Actor 与新的 run_id；Rerun 不继承原始资产作者的豁免。开始同池 PG 事务。
  2. 遵循锁顺序 tenant → actor user → analysis → report_credits；状态检查使用可阻止并发状态更新的共享行锁，分析重跑使用 FOR UPDATE。与 K1／K2 状态写入负责人统一锁顺序。
  3. 复核 active 状态、成员／权限／Key；从 report_credits 当前来源解析套餐，读取固定 UID 政策；在事务中写本轮 actor、套餐与豁免快照。
  4. 普通轮次条件 UPDATE 余额减 1，不足返回 NO_CREDITS；写该 run 唯一消费流水并保存 consume_tx_id。固定管理员不改余额，不写假 consume。
  5. Create 写 analyses；Rerun 确认终态、建立 run_no+1、清旧文档／产物、更新 current_run_id。原始 CreatedBy 保持不变。
  6. 通过 PGQueue.PublishTx 写携带 tenant／analysis／run ID 的新消息，最后一次 Commit。扣费、流水、run、分析、文档清理、队列任意失败全部 Rollback。

worker、恢复和终态

  • 领取任务后检查消息 run_id 与 analyses.current_run_id／analysis_runs.id 一致，持有运行锁。旧轮、终态或重复已完成消息 no-op；不能把旧消息视为一次新的用户 Rerun。
  • 进程中断恢复沿用同一个 run_id 和 consume_tx_id，不产生第二次消费。新用户主动 Rerun 才创建新轮；所有状态、文档及报告关联写入必须检查当前 run。
  • Cancel／markFailed 在同事务中锁分析和当前 run，只有当前活动轮次发生终态跃迁才调用 RefundRunTx。它直接读取该轮 consume_tx_id；exempt／legacy 无消费返回 false，不查 analysis 最近旧流水。
  • refund 仍以 consume_tx_id 唯一索引保证一扣至多一退。状态提交与退款不能分成“先 failed，再尽力回补”的两个事务；回补失败时整笔状态变更回滚并交给任务重试。
  • 补偿退款是系统账务动作，不因原 actor 后来被禁用而拒绝；禁止继续新增外部调用，但已发生供应商成本和合法退款必须结清并可追踪。
关键验收：普通用户完成收费轮次 → 固定管理员免费重跑 → 新轮失败／取消，团队余额不增长，旧成功 consume 不得被退款。反向切换为普通用户重跑时，新轮必须收费。

完成新原子路径及云端证明后，删除 production SetBetaSkipCredits(true) 接线、beta env 启动门槛和 PG 错误分支。推荐移除整个可用 bypass setter，现有 PG fixture 改为真实测试额度；server、worker、E2E 配置和旧断言同步更新，不能留环境变量再次放行普通账号。

7. Python／Go 用量桥接与幂等落库

实际管线经过 Python HTTP 引擎，单独修改未接线的 Go MeteredProvider 无法完成 K4。以下契约覆盖 insight 的多维并发、报告 LLM、retry、JSON 解析失败及晚到事件。

内部接口

接口请求服务端结果
POST /internal/v1/billing/llm-authorizations{call_id,run_id,engine,phase,attempt,model}。call_id 每次实际供应商尝试唯一；不接受 user_id／tenant_id／exempt 决策。从 run 解析 actor／tenant／政策快照，复核当前状态、Key、hard cap及真实套餐；201 返回 call_id、有效期与绑定请求内容的许可。相同请求重放200；异参409；配额拒绝402 TOKEN_QUOTA_EXCEEDED。

两端点只开放内网／loopback 服务路由，要求独立服务认证；普通 JWT、tenant API Key 和浏览器不能写入。事件接口另在 X-LLM-Call-Permit 头提交原调用许可；outbox保留许可直到ACK。秘钥从配置或受控环境注入，不提交到源码、不回显日志。Token计数必须非负，attempt必须与原许可一致，engine／phase按服务端允许值验证。只有 Go 根据运行与许可决定 quota／费用身份；取消后的晚到已授权用量仍须记入事实账本。

每一次供应商调用的顺序

  1. Go pipeline 将当前 run_id 传给 insight／report；共同 LLMClient 在每次供应商调用及每次 retry 前创建 call_id，并申请许可。hard cap 到阈值后拒绝新的普通调用；固定 UID跳过消费闸门，仍建调用记录。
  2. 取得许可后调用既有供应商。返回时立即提取真实 model／usage／request ID，先把事件写入配置的持久 outbox，再解析 JSON 或做完整性判断；发生截断或无效 JSON 的已用 token 不能丢弃。
  3. outbox 使用每事件独立 JSON 文件、临时文件写入、fsync 和原子替换；目录挂载到持久卷，启动及周期重投。相同逻辑事件只用同一 event_id。Go ACK 且确定事务已提交后才移除文件；ACK 丢失时重投不重复入账。
  4. Go 在事务内核对许可、事件 hash和唯一键，插入 usage_events；identity、exempt、quota_tokens 和费用口径全部由服务端补齐。event/call 同参重放无新增事实，异参冲突不覆盖原事实。
  5. 任务失败或被取消仍记录已授权调用成本。已获得正常 usage 的失败输出照常计入真实消费配额；管理员实际 tokens保留但 quota_tokens=0。用户的 report credit 回补与供应商实际成本是两份不同事实。

不能伪造的未知值

  • SSE 开启供应商支持的 usage 返回选项；cache tokens 按该供应商明确口径归一，若已包含在 prompt_tokens 中不得再重复累加。
  • 网络超时、进程崩溃或供应商未返回 usage 时记录 unknown 及调用证据，不能用字符数估计冒充真实 token，也不能把 0 当成核对过的供应商成本。保留 call_id／request ID并列出待对账调用。
  • 无可核对供应商价格时 cost_status=pending；沙箱验收注入有版本的测试价格与真实形式 usage，验证计算和留存。生产实际成本完整性须以配置的真实供应商价格／审计记录单独证明，不能用沙箱通过冒充。
  • 累计 token 查询改用 quota_tokens。实际统计查询仍保留全部 tokens和成本；不通过整 tenant 过滤掉管理员事件。配额来自 EffectiveBudget 的持久套餐源，重启不能回到无限制。
  • hard cap沿用调用前检查语义：已接纳调用的最终真实用量可能跨过阈值，后续新调用被拒。不能截断已发生的真实账务数量；若未来要求 token 预算并发严格预留，需单独定义供应商 max-token预留合同。
