盘古舆情 · CI/CD 体系规划

状态：规划文档（尚未实施）· 2026-09-13 · 本文档只做体系设计，不包含任何已执行的自动化

一、现状与约束（规划依据）

约束对 CI/CD 的影响
仓库公开（github.com/jetchanxxx-tech/yuqing）CI 配置中禁止任何明文密钥；历史上发生过 Bocha key 泄露，密钥扫描必须是硬门禁
生产在国内（阿里云 47.120.20.10）GitHub 托管 runner 到国内服务器连通性不稳定 —— CD 不能依赖外网直达部署
生产服务器低配禁止在服务器上编译；测试二进制本地/CI 交叉编译后上传执行（已实测教训）
无 Docker（用户明确要求）CI 用 GitHub 托管 runner（runner 内部用 Docker 镜像做 PG 服务不违反部署约束）
部署脚本已幂等deploy.sh 可安全重跑 —— CD 可直接复用它，无需重写部署逻辑
测试体系已完备Go 单测/契约（内存版）+ PG 契约（YUQING_TEST_PG_URL gate）+ Python pytest + 生产 E2E 26 用例

二、总体流水线设计

一条主干流水线（push/PR 触发），分四个门禁 + 一条发布线：

代码提交（push / PR）
  │
  ├─ 门禁 1【CI 基础】Go test(内存版) + vet + 前端 build + oxlint + pytest + 密钥扫描
  ├─ 门禁 2【PG 集成】PostgreSQL service 容器 + YUQING_TEST_PG_URL → 全量契约测试
  ├─ 门禁 3【生产 E2E】secrets 凭据 → 打生产站点 26 用例（PR 不跑，仅 main/nightly）
  │
  └─ 发布线【CD】tag 触发 → 交叉编译产物 → 经跳板/自托管 runner → deploy.sh 幂等部署
        （含迁移 yuqing-cli migrate platform + healthcheck 自检回滚门禁）
门禁 3 与发布线不阻塞开发：门禁 1/2 是 PR 合并条件；3 与 CD 只在 main 分支或 tag 上执行。

三、分阶段实施计划

阶段 1CI 基础门禁（预计 0.5 天，风险低）

文件：.github/workflows/ci.yml，触发：push + PR。

Job步骤说明
go-testcheckout → setup-go 1.25 → go test ./... -count=1 → go vet ./...内存版测试本地等价（无需 PG）
frontendsetup-node 22 → npm ci → npm run build → npm run linttsc + vite + oxlint
pythonsetup-python 3.11 → pip install -r engines/requirements.txt → python -m pytest engines/tests/34 用例（无需 scrapling 二进制）
secret-scangitleaks/github-action（或 secretlint）公开仓库硬门禁：任何 sk-/密码命中即红

阶段 2PG 集成测试（预计 0.5 天）

在 ci.yml 增加 job，用 GitHub 的 services: postgres:15 起库：

pg-contract:
  services:
    postgres:
      image: postgres:15
      env: { POSTGRES_USER: yuqing, POSTGRES_PASSWORD: test, POSTGRES_DB: yuqing_test }
  env:
    YUQING_TEST_PG_URL: postgres://yuqing:test@localhost:5432/yuqing_test?sslmode=disable
  steps:
    - run: |
        sudo apt-get install -y postgresql-contrib   # 提供 citext 扩展
        psql ... -c 'CREATE EXTENSION IF NOT EXISTS citext'
    - run: go test ./... -count=1
这正是服务器上人工跑过的同一套真实 PG 契约测试（8 包 PASS），搬进 CI 即可让「真实数据库回归」每次 PR 自动执行。

阶段 3生产 E2E 门禁（预计 0.5 天）

  • 文件 .github/workflows/e2e.yml，触发：push 到 main + 每日 cron（建议 02:17 避开整点）+ 手动 workflow_dispatch。
  • Secrets：E2E_EMAIL / E2E_PASSWORD（生产测试账号）→ 以环境变量注入，沿用现有 spec 的「无凭据即抛错」设计。
  • 步骤：checkout → setup-node → npx playwright install --with-deps chromium → E2E_EMAIL=... E2E_PASSWORD=... npx playwright test --config e2e/production.config.ts。
  • 失败策略：邮件/issue 告警；不自动回滚（E2E 失败先人工判断是功能回归还是数据/凭据问题）。

阶段 4CD 发布线（预计 1 天，需一次协作配置）

核心决策：不在 GitHub 托管 runner 上做部署（到阿里云连通性差）。两条备选路径，推荐 A：

方案机制优劣
A（推荐）
自托管 runner		在阿里云同机房一台 2C2G 小机上装 actions-runner（或直接在生产机的低峰期跑），注册到仓库；tag v* 触发内网直连生产，deploy.sh 直接可用；需要一台跳板资源 + runner 维护
B
Webhook 触发		tag 事件 → GitHub 调服务器上一个小服务（如 yuqing-deployd：校验签名 → git pull → deploy.sh）无 runner 维护；但要在服务器上写并暴露一个带验签的触发端点（攻击面 +1）
# 方案 A 的 CD 流程（release.yml，self-hosted runner）
push tag v1.2.3
  → 门禁 1+2 全绿（release 前强制重跑）
  → self-hosted runner：
       git pull origin main
       YUQING_DOMAIN=... bash scripts/deploy.sh          # 幂等
       YUQING_CONFIG=... bin/yuqing-cli migrate platform # 迁移
       bash scripts/healthcheck.sh --json                # 自检门禁：非 ok 则标记失败
  → 部署成功 → 创建 GitHub Release（changelog 自动生成）
  → 部署失败 → 保留旧二进制自动回滚：cp bin/yuqing-server bin/yuqing-server.bak 后部署，
     失败时 systemctl 指回 .bak（deploy.sh 增加 --backup 段，列入阶段 4 实施项）
生产服务器的「禁止编译」约束同时写入 runner 配置：CD 里的交叉编译在 GitHub 托管 runner 上产出 tar 包，self-hosted runner 只做「解包 + deploy.sh」，全程不在生产机器上执行任何编译器。

四、密钥与安全管理

Secret 名用途位置
E2E_EMAIL / E2E_PASSWORD阶段 3 生产 E2EGitHub repo secrets
E2E_BOCHA_KEYE2E 5.3 数据源写入验证（可选）GitHub repo secrets
DEPLOY_SSH_KEY阶段 4 自托管 runner 登录生产机（密钥登录，禁密码）runner 本地 / repo secrets
BOCHA/DEEPSEEK key仅存在于生产 engines.env，不进任何 CI服务器（chmod 600）
仓库公开：CI 配置文件本身也要过密钥扫描门禁；secrets 只能以 ${{ secrets.X }} 引用，禁止 echo/printenv 输出。

五、回滚与可观测

  • 回滚：deploy.sh 增加备份段（旧二进制 .bak + 旧 dist 快照），CD 失败自动回退；手工回滚：git checkout <last-good-tag> && bash deploy.sh。
  • 部署痕迹：deploy.sh 已写 /opt/yuqing/data/logs/deploy.log；CD 将该日志尾 200 行回传 GitHub Actions 输出。
  • 自检闭环：healthcheck.sh --json 作为部署最后门禁；阶段 4 顺手部署 8.3 节的 systemd timer 定时自检。
  • 告警：E2E nightly 失败 → GitHub issue（actions/github-script 自动创建，防重复去重）。

六、实施排期建议

顺序内容依赖验收标准
1阶段 1 门禁 + 密钥扫描无PR 全绿；故意提交假 key 的测试 PR 被拦截
2阶段 2 PG 集成阶段 1PG job 与服务器手工结果一致（8 包 PASS）
3阶段 3 生产 E2Esecrets 配置nightly 首跑 26 过（或与手工一致）
4阶段 4 CD（方案 A）1-3 + 跳板机资源tag 发布 → 生产更新 → healthcheck ok 全自动

本规划由运维经理制定，实施前需产品负责人确认阶段 4 的跳板资源与发布节奏（建议每周一次 tag 发布，避免生产变更过频）。
