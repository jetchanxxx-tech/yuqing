四、问题与修复（15 项）

阻塞级（导致部署失败）

#问题症状根因修复
1 阻塞 mkdir 晚于日志调用 脚本第 39 行静默退出，日志仅一行 LOG_FILE 位于 $APP_ROOT/data/logs/，但 mkdir 在 5 行之后才执行；tee 写不存在的目录失败，set -euo pipefail 直接终止 目录创建提前到日志函数定义之后
2 阻塞 Go 依赖下载超时 dial tcp 142.250.x.x:443: i/o timeout proxy.golang.org 在境内不可达（Google IP） 自动配置 goproxy.cn + sum.golang.google.cn，可用环境变量覆盖
3 阻塞 venv 创建失败 ensurepip is not available 检测条件用 import venv（基础 python3 自带，必然通过），实际需要的是 ensurepip（独立包 python3.12-venv） 检测改为 import ensurepip
4 阻塞 残缺 venv 被误判 pip: No such file or directory 第 3 项留下的残缺目录含 bin/python 但无 bin/pip；幂等检查只看前者即跳过重建 改用 bin/pip 判定；检测到残缺先 rm -rf 再重建
5 阻塞 二进制命名不匹配 服务起不来，健康检查失败 go build -o dir/ ./cmd/... 按包目录名产出 cli/server/worker，但 systemd unit 引用 yuqing-server 等。日志显示"构建完成"极具误导性 逐个显式 -o $APP_ROOT/bin/yuqing-$pkg
6 阻塞 nginx 校验失败 nginx -t 失败，站点完全不可用 nginx.conf 无条件包含 443 + ssl_certificate 块；跳过 SSL 时证书文件不存在 → 校验失败 → reload 被拒 新增 nginx-http.conf（HTTP-only），按证书存在与否自动选用
7 阻塞 default_server 冲突 外部访问返回 "Welcome to nginx!"，/api 404 Ubuntu 自带的 sites-enabled/default 占着 0.0.0.0:80 的 default_server；IP/无匹配域名时请求全落到欢迎页 部署前扫描并移出冲突站点（备份到 /root/），本应用标记 default_server。注意：仅改名无效，include 会加载目录下所有文件
8 阻塞 forum 引擎语法错误 yuqing-forum 反复重启，日志被堆栈淹没 中文文案内嵌 ASCII 双引号，提前终止 Python 字符串字面量 → SyntaxError 全量改写为全角引号「」，并把约束写入 docstring；deploy.sh 增加 py_compile 预检

非阻塞级（功能缺失或环境障碍）

#问题影响修复
9 环境 SSH 密码认证失败 三个不同密码均被拒，无法连接 根因不是密码：Windows 原生 sshpass 与 MSYS ssh 的 pty 机制不兼容。改用 OpenSSH 内置 SSH_ASKPASS
10 环境 GitHub 访问中断 GnuTLS recv error，无法 clone/pull 本地打包（392 KB）+ SCP 上传，绕过 GitHub
11 功能 Scrapling 安装失败 数据采集组件未就绪 scrapling install --chromium 参数不存在，且 2>/dev/null 吞掉错误。去掉参数与重定向，改用 Playwright 缓存目录判定
12 功能 Python 引擎未部署 数据采集链路完全未激活 新增 5 个 systemd unit（yuqing-{query,media,insight,report,forum}），deploy.sh 补齐部署流程
13 功能 platform_admin 无法获得 /admin/* 全部 403，管理后台不可达 注册流程只创建 tenant_admin，且内存 store 无法用 CLI/DB 写角色。新增引导机制：YUQING_BOOTSTRAP_ADMIN_EMAIL 指定的邮箱注册即获 platform_admin
14 兼容 nginx 1.24 不支持 http2 on; 配置校验失败：unknown directive "http2" 该指令需 nginx 1.25.1+。改用 listen 443 ssl http2 参数形式
15 功能 Login 丢失 platform_admin 注册返回 [tenant_admin platform_admin]，重新登录只剩 [tenant_admin] → 管理后台再次 403 第 13 项修复只改了 Register，Login 仍只回显成员表里的基础角色。抽出 rolesFor() 共享方法供两者调用
第 15 项的启示：这是修复第 13 项时自己引入的回归 —— 只改了写入路径（注册），漏了读取路径（登录）。同一份角色逻辑存在两处实现，改一处必然漏另一处。修复方式不是「再补一处」，而是抽出共享方法消除重复。
另有 1 项误判（非服务器问题）：本机 curl 访问 HTTPS 报 CRYPT_E_REVOCATION_OFFLINE。经查是 Windows Schannel 客户端无法连接证书吊销服务器所致，服务器本身正常（服务器本地 curl 与 openssl 均通过）。Windows 客户端需加 --ssl-no-revoke。

八、经验总结

这 15 个问题没有一个是静态检查能发现的

部署前项目状态：bash -n 语法通过、go vet 干净、332 个单元测试全绿、5 角度代码审查无告警。但首次真实部署仍然连续失败 4 轮。

原因是这些缺陷依赖目标环境的特定条件才会显现：

  • 执行顺序缺陷（#1）—— 只在特定 PATH/目录状态下触发
  • 网络地域限制（#2、#10）—— 只在境内网络暴露
  • 镜像版本差异（#3、#4、#14）—— 依赖具体发行版的包拆分方式
  • 工具默认行为（#5、#7）—— Go 的 -o dir/ 命名规则、nginx 的 default_server 优先级
  • 字符编码陷阱（#8）—— 中文文案里的半角引号

四条可复用的教训

#教训
1构建成功 ≠ 部署成功。「Go 二进制构建完成: cli server worker」这行日志看起来是成功，实际产出的文件名与 systemd 期望的完全不同。日志应输出预期路径而非目录列表。
2幂等检查要查「可用」而非「存在」。残缺 venv 有 bin/python 却没有 bin/pip；只判断存在会跳过重建，把损坏状态固化下来。
3配置文件不应假设单一部署形态。nginx.conf 假设「一定有证书」，导致无域名部署（完全合理的场景）整个站点不可用。模板应按条件选择。
4改一处不如抽一处。角色构建逻辑同时存在于 Register 和 Login，修复时只改前者导致回归（第 15 项）。发现同一逻辑有两份实现时，正确做法是抽成共享方法，而非分别修补。
结论：deploy.sh 现已覆盖从系统依赖到 HTTPS 证书的完整流程，且所有修复都有真实环境的失败证据支撑。重复部署不会再遇到上述问题。
